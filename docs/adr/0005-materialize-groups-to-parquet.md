# Materialize Groups to Parquet, with the Filter List still the source of truth

A Slice used to be a filter chain and nothing else: a row in `slices` holding `Filter[]`, plus an optional `base` chain silently prepended to every other. Nothing was stored for it, so every view re-read `event_log.parquet` and re-ran the whole chain — the tree, the distributions, the statistics table and the per-step impact funnel, each on its own. A Slice existed only as a recipe, and the cost of that recipe was paid again on every render that needed it.

Groups replace Slices, and applying a Group's Filter List now writes `{app_data}/projects/{project_id}/groups/{group_id}.parquet`. Downstream commands take Group ids and read those files; they no longer receive filter chains at all. The Filter List stays the source of truth — the Parquet is its product, and is never edited, never treated as an independent object, and never the thing a Filter List is recovered from.

The alternative was to keep everything derived and lean on caching in memory. That is what the app did, and it is why `slices.svelte.ts` carried two separate caches — an in-memory `impacts` map and the persisted `stats`/`statsKey` columns — both keyed by a JSON dump of the effective chain, and why the case counts on screen could disagree with each other during an edit. Materializing collapses both caches into one artifact that either exists or does not.

**Materialization happens only on Apply.** Filter editing is a draft held in component `$state`; add, delete, drag-reorder and clear-all are array operations on it, and nothing is written until the user commits. A debounced `filters_impact` call keeps the per-step funnel live during editing, reading the Event Log in memory and writing nothing. So the expensive path has one trigger, and the responsive path has no side effects. The funnel's numbers belong to the draft and are labelled as such; they are not the Group's case count until Apply says so.

**Ordering follows the lifecycle rather than crash-safety discipline.** A Group's row is created when the user creates the Group — names it, picks a colour — before any filter exists, so the row precedes the file naturally and a Parquet without a row is impossible by construction. Deletion reverses it: the file goes first, then the row, and a failure at either step deletes nothing. There is no transaction spanning SQLite and the filesystem, so one inconsistency remains reachable: a crash between a successful file delete and the row delete leaves a row with no file. That state is indistinguishable from never-applied and is repaired by re-applying, so `loadGroups` checks the file exists and treats a missing one as unmaterialized. No orphan sweep is needed in either direction.

`stats` carries the whole of that signal. Apply is already reading the filtered frame to write the file, so it computes the Group's `EventLogStats` in the same pass and writes them with the row. A non-null `stats` therefore means "this Group has a Parquet", and `stats_key` and `parquet_key` — both drafted, neither built — are unnecessary: applied filters change at exactly one moment, and that moment rewrites the stats rather than invalidating them.

**Consequence:** Rust stops being handed filter chains for reads. `directed_tree`, `list_variants`, `node_distributions`, `group_stats` and `shared_cases` take Group ids and resolve them to paths themselves, which also ends the frontend's habit of composing a base chain before every call. Filters survive on the two commands that still do filtering work: `filters_impact` (the draft preview) and `apply_group` (the write). The `base` Slice concept is deleted outright; copying a Filter List between Groups replaces the one thing it was good for.

**Cost accepted:** disk. A project with ten Groups keeps ten filtered copies of its Event Log alongside the original. Parquet's columnar compression makes that cheaper than it sounds, the files are deleted with their Group and with their project, and the app is local-first with no storage quota to respect. The trade is disk for latency, and this application spends most of its time re-reading the same rows.
