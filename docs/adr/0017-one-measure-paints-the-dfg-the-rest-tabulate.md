# One measure paints the DFG, the rest are read in a table beside it

The DFG printed case and event counts and nothing else. Every other figure the build already measured — Service Time, Waiting Time, an Amount column, a Custom Attribute — reached the reader only one activity at a time, through the detail panel, after a click. The graph could show where the cases go but never where the time or the money goes, which is most of what a comparative process map is asked for.

The build already ships all of it: `DfgNode.attributes` carries a Summary per Group and a Significance Test for every attribute asked for, and `Transition.wait` carries the same for every pair the log holds. Nothing new is computed and no Rust changed. What was missing was somewhere to read it.

**One measure is painted; all of them are tabulated.** The graph paints exactly one measure as the shade and the figures on the node faces, chosen in a **Graph paints** select. Everything else lives in the **Measures by activity** table, one row per activity drawn, one column per measure, each cell carrying both Groups' figures. A node face that printed every measure would be a spreadsheet in a box: four figures per Group on a 170px node, unreadable at any zoom, and unreadable in a split where both panels have the same problem twice.

The table is the second half of the feature, not a detail view. Columns sort, and the Δ column follows whichever column the table is sorted on, so "which activity differs most in waiting time" is one click. Δ is shaded on the `--effect-*` ramp only where the Significance Test came back significant, which is the same ramp and the same rule the tree's effect chips use. A row and its node point at each other: hovering either lights both, and picking a row selects the activity.

**Measures are not Frequencies.** `Measure` is what a face prints: either frequency, or an attribute read off its Summary. `Frequency` — the old `Measure` — is the unit the fold counts in, and it is still what cuts the paths and places the boxes, because a path cut by magnitude of money is not a process map. So painting an attribute never relays the graph: `frequencyOf` hands ELK `cases` for every attribute measure, and only switching between Cases and Events can move a box.

**Only numeric attributes can be painted.** A categorical attribute has no magnitude to shade or rank by, so it stays out of the select and out of the table, and is read in the activity's detail panel where its distribution belongs.

**Edge width encodes one of two things**, and Show picks which: the frequency, or the mean Waiting Time over every case that ran the pair. A pair with no wait measured is drawn at the minimum rather than falling back to its frequency, so one canvas never mixes the two units.

**Frequency and Time are the two views, and one field sets both halves.** Show reads Frequency or Time: Frequency puts the activities on cases and the paths on counts, Time puts the activities on Service Time and the paths on Waiting Time, which is what every other process map calls the time view. Neither is pressed when Graph paints has been set to something else, which is the escape hatch for a column of the reader's own. Service Time is asked for from the start so that switching views redraws rather than rebuilds.

**Waiting Time is always measured, and printing it is a switch.** The invoker asks for it whatever the attribute selection holds, because the edges are drawn from it: that is what lets the Waiting Time edge width work on a graph where nothing was ticked. It is therefore not offered in the DFG's Attributes tested list, which is what the _activities_ are tested on, and whether the wait prints in a bubble on each edge is a view switch beside the edge width. The selection opens empty, as it did before any of this.

**A wait bubble lights its own path.** Two edges that run side by side have the same stops free or taken all the way down, so a label with nowhere to go is pushed off its route to one side rather than sliding along it, by its own width, since a shorter push cannot part two labels either. The shortest routes are placed first, having the fewest stops that clear anything, and a pill is measured with the room its Groups' dots take, not its text alone, which is what let two short labels sit on top of each other. Pushing a label off its route weakens which edge it belongs to, so clicking a bubble lights its edge, the same lighting a Variant row uses.

**Two sources meet in one row and they describe different things.** A frequency comes from the fold, so it follows the Behaviour and Paths sliders. An attribute's Summary is what Rust measured over the built Variants, so it stands still while the sliders move. Recomputing a Summary per cut would mean shipping per-Variant distributions or rebuilding on every slider tick, and neither is worth it: the panel says which is which in its footnote instead.

**The ramp's hue is a choice, except where it would lie.** Shades are read in the Group's own hue by default, which is what the tree does and what makes shade and membership one colour. Nine fixed ramps are offered behind the legend, as a grid of the ramps themselves: the strip between the two bounds is the control, because a panel this narrow has no room for a second one beside it. **An activity one Group alone reaches keeps that Group's colour whatever is chosen**: the ramp applies to the activities the comparison shares, which are the Original's grey without it. That alone is not enough, because a shared activity shaded in the hue of one of the Groups reads as belonging to it, so a ramp within 50 degrees of a compared Group's own hue is not offered at all, and one in use when a Group claims its hue falls back to the Group ramp. A node with no figure keeps its Group's flat tint for the same reason: there is nothing to read on the ramp there.

**A wait on an edge is one label per Group, not one string.** Each part carries its Group's dot, as the node faces do, so a reader never has to work out which figure is whose by position. When every Group waited the same the label collapses to one figure behind all the dots, because two identical numbers side by side say less than one.

**The panel carries its own attributes control**, so adding one does not mean leaving the table. Picking a row selects the activity on the graph, which draws a ring around it, and the panel names what is selected with a button that hands over to the detail panel.

**Consequence:** `DfgView` carries the painted measure, the edge measure and the ramp, all view state like the sliders, so none is persisted and all are lost on reload. A measure naming an attribute the build no longer holds falls back to Cases rather than painting nothing. The right of the canvas holds one panel at a time: the measures of every activity, or the detail of one. The measures panel is dragged wider or narrower from its left edge, clamped so the canvas keeps room.
