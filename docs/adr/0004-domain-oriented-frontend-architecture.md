# Organize the frontend by domain rather than by kind of file

`src/lib/` was organized by what a file *is* — `components/`, `state/`, `projects/`, plus loose modules (`tree.ts`, `filters.ts`, `distributions.ts`, `types.ts`). Reading how one feature works meant opening five directories, and `components/projects/` had grown to 35 files covering every feature in the app. It is now organized by what a file is *about*: six domains under `src/lib/`, each owning its components, state, Tauri invokers, invocation contracts, utilities and tests.

The domains are `event-log/`, `filters/`, `slices/`, `statistics/`, `tree/` and `distributions/`. Each maps to a module under `src-tauri/src/`, and four of them map to a route under `/app/projects/[id]/`, so a URL names the directory that serves it. Dependencies run one way — `statistics | tree | distributions → slices → filters → event-log` — and nothing points back up. `distributions/` also imports from `tree/`, which is consistent: it drills into a node of a tree that already exists.

`src/lib/components/` is now only what is genuinely shared: `ui/` for shadcn primitives, `layout/` for app chrome, and one folder per own reusable component (`virtual-list/`, which colocates its Svelte file, its windowing arithmetic and its test). `format.ts` stays global at `$lib/format.ts` — 21 importers across every domain and no domain knowledge. `$lib/utils.ts` and `$lib/hooks/` stay put because `components.json` pins those aliases and the shadcn CLI rewrites imports to them on every `add`.

Three calls went against the obvious reading of that principle. **`db/schema.ts` stays one file** rather than splitting each table into its owning domain: seeing every table in one place is worth more than strict ownership, so it imports persisted types from four domains and that is accepted. **`statistics/` stays its own domain** even though it owns no state and no types — every input comes from `slices/` — because keeping directories mapped one-to-one to routes makes navigation predictable. **Project and event log are one domain**, not two: `Project.columns` is `ColumnMapping[]` and `createProject` calls `addProject`, so splitting them would have them referencing each other in both directions, and `event_log/commands.rs` already treats them as one module.

Conventions that follow from this: types have exactly one home and are never re-declared — anything Rust serializes lives in `<domain>/invokers/types.ts`, everything else in `<domain>/types.ts`, including shapes that are persisted to SQLite but never cross `invoke` (`TreeSettings`). One invoker file per Tauri command, named after it, so `invoker → contract → Rust command` is one-to-one; components call the invoker rather than `invoke()` directly. Kebab-case filenames throughout, matching the ~150 CLI-generated files in `components/ui/` that cannot be renamed. Deep imports and no barrel files, so a dependency is visible in the import line. Tests live at `<domain>/tests/{components,state,invokers,utils}/`, except for shared components, which keep their test beside their source.

**Consequence:** the filter vocabulary is now one module per filter kind under `filters/filters/`, mirroring `src-tauri/src/filters/` — each kind owns its type, modes, copy and its arm of `describeFilter`/`isFilterComplete`, and `filter.ts` holds only the union and the dispatch, the analogue of `mod.rs::apply_one`. Adding a filter kind is one new file plus two lines. Vitest was installed alongside this (jsdom + Testing Library, config in `vitest.config.ts` so nothing leaks into the Tauri-tuned `vite.config.js`); the two existing hand-rolled `node:assert` scripts were converted.

**Deferred**, both because they are rewrites rather than moves and belong in their own reviews: splitting `filters/components/filter-editor.svelte` (833 lines, ~18 `$state` variables shared across kinds) into per-kind editors, and thinning the four fat routes — `distributions` 393, `new` 233, `filters` 219, `tree` 176 lines — whose regions can be extracted into domain components. End-to-end tests are blocked rather than deferred: `tauri-driver` supports Linux and Windows only, so Playwright cannot drive the real Tauri window on macOS, and testing these flows in a browser would mean mocking `invoke()` and `plugin-sql` wholesale.
