# The tree and the DFG share one toolbar and one Variants picker

The DFG drew every Variant its Groups held. Narrowing it meant moving the Behaviour coverage slider, which hides Variants from the drawing but leaves them in the aggregation: the node counts, the attribute Summaries and the Significance Tests still described cases the user could no longer see. The tree has had a manual picker since it shipped, and it cuts before aggregating, so the two views disagreed about what a comparison was about.

The DFG now takes a Variant selection too. `dfg` accepts an optional list of Variant keys and `build::aggregate` filters the cases down to them before anything is accumulated, the way `directed_tree` does. The keys are the same strings on both sides: `analysis::VARIANT_KEY_SEP` is the separator `tree::variant_key`, `list_variants` and the frontend's `variantKey` all join activity names with, so a selection made in one picker names the same cases in the other. The selection is persisted per project in `dfg_settings` and keys the in-memory graph cache, so changing it rebuilds and moving a simplification slider still does not.

The first attempt copied the tree's panel into `dfg/components/`: three components and the staging state, about 750 lines, duplicated with the nouns changed. Instead the picker is now one component.

The panel, its rows and the toolbar field live in `src/lib/components/variant-panel/`. They hold no state and know neither view: they take the compared Groups, the Variant rows, the staged set, which keys the canvas is drawing, and the callbacks that stage, apply and close. One prop, `canvas`, is either `"tree"` or `"graph"` and decides the icon a drawn row carries and the noun the copy uses.

The staging is a factory, `tree/state/variant-selection.svelte.ts`. Both views stage the same way — an edit held in memory that only Apply writes through — and differ in two places, which are its options: where the selection is persisted, and what an empty one means. `"coverage"` is the tree's, where empty means "not chosen yet" and the first load re-seeds it from `DEFAULT_COVERAGE`; `"all"` is the DFG's, where empty means every Variant and is left alone, matching what the graph showed before the panel existed.

Each domain keeps a thin adapter that binds its own state to the shared panel and counts the Variants its canvas is drawing — `visibleNodes` for the tree, the Behaviour cut's kept keys for the DFG. The Variant vocabulary itself stays in `tree`: `ResponseVariantRow`, the `list_variants` invoker and `utils/variants.ts`. That makes `dfg → tree` a dependency edge, alongside the `distributions → tree` that already existed.

The rest of the toolbar followed. The DFG kept its settings in a single "Graph" popover while the tree had had a row of fields since `#80`, so the two views disagreed about where a build input is changed. The DFG now opens on the same row: Compare groups, Variants, Attributes tested. Two of those three were identical markup in both toolbars, so they are one component each — `groups/components/compare-field.svelte`, which owns the field and the `CompareDialog` behind it, and `custom-attributes/components/attributes-field.svelte`, which owns the field and the list of attributes to pick from. Each lives in the domain whose vocabulary it reads, so neither adds a dependency edge.

The attributes field holds no state. The two views commit a change differently — the tree keeps a draft until the popover closes and writes it to `tree_settings`, where it invalidates the build; the DFG applies each toggle to an in-memory selection and rebuilds — so the field takes `selected`, `onToggle`, the caption and the note, and each view's `build-settings.svelte` keeps its own semantics. The simplification sliders stay in the DFG's "Graph" popover; moving them into the toolbar is a separate change.

**Consequence:** a change to any of these is made once and both views get it, which is how the DFG inherited the Venn selector and the shared `VariantPath` chevrons it had been missing. The cost is that `components/variant-panel/` is not domain-free the way the rest of `components/` is: it imports the `Group` and `ResponseVariantRow` types. It imports no state, so the coupling is to the vocabulary, not to either view. Moving the Variant vocabulary out of `tree` into a domain of its own would remove the `dfg → tree` edge and is the next step if a third view needs it.
