# Exclude a Group with a filter kind, not by negating its Filter List

Two Groups may overlap, and the most common comparison in the app — a Group against the whole Event Log — always does, because one side contains the other. The app reports the shared case count when a Comparison is chosen and offers to build a Group without those cases instead. This decides how that Group is built.

The obvious construction is to negate the other Group's Filter List: if A is `premium = gold`, offer `premium ≠ gold`. It works for exactly one filter and breaks at two. A Filter List is an AND pipeline, so `[premium = gold, region = north]` means *gold AND north*, whose complement is *not-gold OR not-north* — and there is no OR anywhere in the filter model. The negated list `[premium ≠ gold, region ≠ north]` is a different and strictly smaller set, silently dropping every gold-but-south case with no error to notice. The `keep_selected`/`trim` modes have no complement to write down at all: they cut events out of surviving traces rather than selecting cases, so "the cases this did not select" is not a predicate over columns.

Removing the intersection at event level was rejected for a related reason. Deleting the events a case shares with another Group leaves a trace no case ever walked — a case going `Register → Review → Approve → Pay` that loses only its `Review` event becomes a variant that does not exist in the data, and the tree would then show a path nobody took. Doing it Group by Group in sequence, as a first sketch proposed, is also order-dependent, which is not what an intersection means.

So exclusion is a filter kind: `case_not_in_group(group_id)` keeps the cases whose case id does not appear in the named Group. It is set difference over case ids, which is what `shared_cases` already computes to report the overlap in the first place. It works for a Filter List of any length in any mode, needs no negation algebra, and composes — a Group excluding two others simply carries two of them. It also fits the extension path the codebase already documents: one file in `filters/kind/`, two lines in `filters/kind/filter.ts`, one editor plus one `{:else if}`, mirrored by one file in `src-tauri/src/filters/`.

**Consequence:** filters can now reference Groups, so Groups form a dependency graph where they previously formed a flat list. Deleting a Group that another excludes is allowed and **cascades**, with the confirmation naming every dependent Group that will go with it — blocking the delete instead would leave the user unable to remove a Group without first hunting down what points at it. The graph is derived by scanning Filter Lists whenever it is needed, never stored as edges: a second copy of the relationships is a second thing that can be wrong.

**Cost accepted:** this filter kind is not a predicate over the Event Log's columns like every other one, so it is not portable — a Filter List carrying it means nothing outside the project that holds both Groups. Copying such a list to another project, once that is possible, has to strip it. It is also the reason Group ids must never be reused: a copied Filter List can carry `case_not_in_group("k3n8vq2p")`, and an id handed out twice would leave that filter silently pointing at a different set of cases. Ids are eight random base62 characters rather than a per-project counter precisely so that reuse cannot happen.
