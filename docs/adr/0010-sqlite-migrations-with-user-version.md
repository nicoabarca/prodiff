# SQLite schema changes ship as drizzle-kit migrations tracked by `user_version`

The app used to create its tables with `CREATE TABLE IF NOT EXISTS` at every startup. That cannot add or change a column in a database that already exists, and once the app is installed on other machines every schema change has to reach databases holding real Projects.

Schema changes are now migrations. `drizzle-kit generate` compares `schema.ts` with its snapshot and writes the SQL into `src/lib/db/migrations/`, ordered by `meta/_journal.json`. SQLite rewrites whole tables for most column changes, and drizzle-kit writes that sequence itself. drizzle's own migrator reads the folder with Node's `fs` and cannot run in the webview, so `src/lib/db/migrate.ts` applies the files. The app bundles them with `import.meta.glob`, and `scripts/seed.ts` reads the same files from disk. Both call the same `migrate`, so a seeded database and an app database are always at the same version.

The version lives in `PRAGMA user_version`, a number SQLite keeps in the file header, rather than in a bookkeeping table. Migration `n` in the journal sets it to `n + 1`. `tauri-plugin-sql` has its own migrations, but they run only when the app loads the database and keep their own table, which the seed would have to reproduce. Each migration runs as one script, `BEGIN; ...; PRAGMA user_version = n; COMMIT;`, because the plugin pools connections and a transaction split across calls could land on two of them.

Migrations only go forward. The updater never installs an older build, so there are no down migrations. A database whose version is higher than the build knows is refused, not opened. Before running anything on a database that already has data, the app writes a copy with `VACUUM INTO`. A Rust command creates `{app_data}/backups/` and prunes it to the last three copies, since the webview has no file system access. A failure replaces the app with a screen that names the copy.

**Consequence:** a migration that has shipped is never edited. Changing its SQL would leave databases already past it with a different schema from new ones. Data changes, such as reshaping the Filter JSON in a column, are custom migrations in SQL, using SQLite's `json_*` functions. The Parquet files are not versioned. They can be rebuilt from `original.{ext}`, the Column Mapping and the Filter Lists, and a change to their shape is handled when it first happens.
