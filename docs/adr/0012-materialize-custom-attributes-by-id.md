# Custom Attributes are Parquet columns named by id, parsed once in TypeScript

A Custom Attribute is a formula such as `[expense] / [points]` that the user names and then picks in the tree, the graph, the data table and the Filters like any other attribute. This records how it gets there.

**Materialized, not computed on read.** Every read command takes the Column Mapping from the frontend and resolves attributes by column name, and the numeric filter bounds any column it is given. A formula written into the Parquet as a real Float64 column, plus one synthetic `role: "other"` entry in the Column Mapping the views send, reaches every one of those paths without any of them learning that the column is not from the uploaded file. Computing the column on read instead would put a formula evaluator in front of `read_event_log` and `read_group` and make every command pay for it on every call.

**The column is `fx_{id}`, never the name.** The name lives only in SQLite. Tree settings, graph settings, Filters and every payload refer to the column, so a rename is one row update: no Parquet rewrite, no Filter List to patch, nothing cached that could show the old name. It is the rule Groups already follow, ids everywhere and names joined back in the frontend. Ids are eight random base62 characters and are never reused, since a Filter List may name the column.

**Apply rewrites each file once, in parallel, and only for what changed.** A Parquet file cannot gain a column in place: every row group holds one chunk per column, so any new column means writing the file again. What Apply avoids is recomputation. It receives the attributes to set and the ids to remove, reads each file (the Event Log and every applied Group), adds or overwrites the set columns, drops the removed ones, carries every other column through untouched, and writes a sibling that is renamed into place once every file has succeeded. The files do not depend on each other, so they are written on separate threads. Groups are not re-filtered: an event-scoped formula reads only its own row, so computing it on a Group's rows gives the same values as computing it on the Event Log and filtering afterwards. The same diff applied twice gives the same files, so an interrupted Apply is completed by the next one.

**One parser, in TypeScript.** The editor needs the parse for chips, blocks and error positions, so the grammar lives there. SQLite stores the text; Apply sends the parsed tree as JSON, Rust deserializes it into an enum, checks that every column it names exists and is numeric, and folds it into a Polars expression. Polars' `sql` feature was rejected: it accepts all of SQL rather than our five rules, reports errors in SQL terms, and would still leave the frontend without a parser.

**Consequence:** the Parquet files now also depend on the Custom Attributes, so rebuilding them from `original.{ext}` must re-apply those too. A column a formula reads cannot be hidden or retyped, and a Custom Attribute a Filter List reads cannot be deleted, so no attribute is ever left computed from something the user can no longer see.

**Cost accepted:** row-wise evaluation per file is correct only while formulas are row-wise. Case aggregates such as `case_sum` would give a different value on a Group whose Filter List trimmed events than on the whole Event Log; when they are added, that difference has to be decided, not inherited.
